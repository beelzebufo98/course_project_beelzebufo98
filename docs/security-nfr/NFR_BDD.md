# NFR_BDD.md
## BDD-сценарии для нефункциональных требований (Wishlist Project)

Feature: Контроль доступа
NFR-01: Только владелец видит/меняет свои желания; чужой доступ запрещён

Scenario: Запрет доступа к чужим данным возвращает 403
  Given есть пользователь A (owner) с 2 записями wishes
    And есть пользователь B (не владелец)
    And пользователь B аутентифицирован валидным токеном
  When пользователь B вызывает GET /wishes?owner_id=<A>
  Then ответ имеет статус 403
    And тело ответа не содержит данных о записях пользователя A
    And событие отказа доступа зафиксировано в логах

---

Feature: Аутентификация
NFR-02: JWT обязателен для защищённых эндпоинтов, TTL соблюдается

Scenario: Доступ к защищённому эндпоинту без токена возвращает 401
  Given сервис запущен
  When пользователь вызывает POST /wishes без заголовка Authorization
  Then ответ имеет статус 401
    And тело — в формате application/problem+json

---

Feature: Валидация пользовательского ввода
NFR-03: Некорректные значения не меняют состояние и дают 400

Scenario: Негативная цена отклоняется
  Given авторизованный владелец
    And в БД нет записи с title="Price"
  When пользователь вызывает POST /wishes с { title:"Price", price_estimate:-100 }
  Then ответ имеет статус 400
    And запись "Price" отсутствует в БД
---

Feature: Формат ошибок
NFR-04: Все ошибки возвращаются как application/problem+json без PII(Personally Identifiable Information)

Scenario Outline: Ошибки имеют корректный формат и не содержат PII
  Given авторизованный владелец
  When пользователь делает некорректный запрос <method> <path> с телом <body>
  Then Content-Type = "application/problem+json"
    And тело содержит поля type, title, status, detail
    And тело не содержит персональных данных

---

Feature: Производительность списка желаний
NFR-05: p95 для GET /wishes ≤ 200 мс при 30 RPS

Scenario: p95 листинга держится под порогом на stage
  Given сервис развернут на stage и нагрузка 30 RPS на GET /wishes в течение 5 минут
  When запускается нагрузочный тест
  Then p95 времени ответа ≤ 200 ms
    And ошибка по длительности не превышает порог в 10% по сравнению с предыдущим релизом

---

Feature: Экспорт данных
NFR-06: Только данные владельца; ограничения по размеру и времени

Scenario: Экспорт возвращает только записи владельца
  Given авторизованный пользователь A с 3 записями
    And существует пользователь B с 5 записями
  When пользователь A вызывает GET /export
  Then тело ответа содержит только 3 записи пользователя A
    And отсутствуют записи пользователя B

Scenario: Экспорт укладывается в лимиты размера и времени
  Given сервис развернут на stage
    And подготовлены тестовые данные объёмом до 5 МБ на пользователя
  When запускается 10 RPS запросов к GET /export в течение 5 минут
  Then p95 времени ответа ≤ 500 ms
    And размер каждого ответа ≤ 5 MB

---

Feature: Безопасность зависимостей (SCA)
NFR-07: High уязвимости не допускаются; реакции ≤ 2 дней

Scenario: CI проваливается при High-уязвимостях зависимостей
  Given в репозитории включён шаг CI "pip-audit"
  When в зависимостях обнаружены уязвимости уровня High
  Then джоб CI завершается со статусом failed
    And создаётся issue со сроком решения ≤ 2 дней с момента обнаружения

---

Feature: Целостность и устойчивость данных БД
NFR-08: Нарушения FK вызывают отказ записи; миграции стартуют быстро

Scenario: Нарушение внешнего ключа приводит к отказу записи
  Given в схеме БД включены внешние ключи
  When выполняется INSERT записи wish с owner_id, которого не существует
  Then операция завершается ошибкой БД
    And в таблице wishes отсутствует вставленная строка

Scenario: Холодный старт миграций укладывается в 2 секунды
  Given пустая БД и настроенные миграции
  When сервис запускает миграции на холодном старте
  Then общее время применения миграций ≤ 2 seconds
