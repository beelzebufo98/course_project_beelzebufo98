# ADR-001: Единый формат ошибок RFC 7807

Дата: 2025-10-19
Статус: Accepted


## Context
Изначально сервис возвращал ошибки в разных форматах: где-то `{"error": ...}`, где-то `{"detail": ...}`.
Это мешало автоматизированному тестированию и затрудняло корректную обработку ответов.
Также отсутствовал механизм трассировки.

В **NFR-04** зафиксировано требование:
> Все ошибки должны возвращаться в формате **RFC 7807**, без утечки PII и с понятным статусом/описанием.

Основные проблемы, которые нужно было решить:
- унифицировать формат ошибок по стандарту RFC 7807;
- добавить `correlation_id` для трассировки запросов;

## Decision
Введён централизованный класс `ApiError`, отвечающий за генерацию ответов в формате **RFC 7807**.
Теперь все пользовательские ошибки наследуются от `ApiError`.

**Реализация (`app/__init__.py`):**
```python
from uuid import uuid4
from fastapi.responses import JSONResponse

class ApiError(Exception):
    def __init__(self, code: str, message: str, status: int = 400):
        self.code = code
        self.message = message
        self.status = status
        self.correlation_id = str(uuid4())

    def to_json(self) -> JSONResponse:
        payload = {
            "type": self.code,
            "title": self.code.replace("_", " ").capitalize(),
            "status": self.status,
            "detail": self.message,
            "correlation_id": self.correlation_id,
        }
        response = JSONResponse(
            status_code=self.status,
            content=payload,
            media_type="application/problem+json",
        )
        response.headers["X-Correlation-Id"] = self.correlation_id
        return response
````

**Интеграция:**

* В `main.py` зарегистрирован обработчик
* Все роутеры выбрасывают исключения одинакового типа.

**Формат ответа:**

```json
{
  "type": "not_found",
  "title": "Not found",
  "status": 404,
  "detail": "resource not found",
  "correlation_id": "a7c3c208-0b94-4bb3-8c67-6db9cbf250d1"
}
```

## Alternatives

| Вариант                                  | Плюсы                                           | Минусы                                            |
| ---------------------------------------- | ----------------------------------------------- | ------------------------------------------------- |
| Использовать стандартный `HTTPException` | Простота                                        | Нет `correlation_id`, поля отличаются от RFC 7807 |
| Отдельный middleware с ручной обработкой | Централизованность                              | Более сложная настройка и тестирование            |

## Consequences

**Плюсы:**

* Все ошибки единообразны и тестируемы.
* Поддерживается `application/problem+json` и `X-Correlation-Id`.
* Повышена прозрачность и трассируемость инцидентов.
* Код и тесты согласованы.

**Минусы:**

* Нужно соблюдать единообразие при создании новых эндпоинтов.

## Security impact

* Закрывает риски:

  * **R3:** Утечка PII в ошибках API.
  * **R12:** Непрозрачные ошибки мешают тестированию.
* Связан с угрозой **F1 – Info Disclosure (STRIDE)**.
* Исключает показ стека и SQL-деталей пользователю.
* `correlation_id` упрощает расследование инцидентов без раскрытия внутренних данных.


## Rollout plan

1. Добавить `ApiError` в `app/__init__.py` и зарегистрировать обработчик в `main.py`.
2. Заменить все `HTTPException` и `JSONResponse` для ошибок на `ApiError`.
3. Проверить e2e-тесты:

   * `test_errors.py::test_problem_response_has_correlation_id`
   * `test_users.py::test_user_not_found`
   * `test_wishes.py::test_update_wish_not_found`
4. Проверить заголовок `X-Correlation-Id` в stage-логах.
5. В будущем — добавить middleware для логирования по `correlation_id`.
